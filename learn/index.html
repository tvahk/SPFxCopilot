01 The big picture

Four things sound like "an agent" but aren't the same. Get them straight and the rest is easy.

One sentence: A SharePoint Copilot App is an SPFx solution that bundles one or more Copilot Components (your React UI rendered inside Microsoft 365 Copilot) together with a declarative agent definition (manifest + instructions that make Copilot discover, describe, and call them).

Host

M365 Copilot

The chat surface (canvas) your agent appears in.

Config

Declarative agent

Manifest + instructions + knowledge + actions. JSON & text, no model code.

Your code

Copilot Component

React UI in the canvas. Extends BaseCopilotComponent.

Capability

Tool → Action

Each component tool (Zod-typed) surfaces to the agent as a callable action.

When is SPFx the right way to build a Copilot agent?

There are five ways to extend Copilot. SPFx is one lane - powerful, but not always the answer. Pick the lightest tool that does the job.

OptionCode levelCustom UI in Copilot?Best when…
SharePoint Copilot App (SPFx) ← this hub Pro-code (React/TS) Yes - inline + fullscreen You need interactive UI inside Copilot (dashboards, wizards, forms) or a full-screen app, tight SharePoint/Graph integration, and you already do SPFx. Auto-hosted in your tenant.
Agent Builder (in Copilot) No-code No You want a quick declarative agent grounded on your files/sites with instructions + starters. Fastest path; no UI.
Copilot Studio Low-code No (chat + connectors) Citizen devs; conversational flows over many connectors; topics/triggers without writing code.
Declarative agent via Agents Toolkit / TypeSpec Pro-code No custom in-canvas UI You want pro-code instructions + knowledge + API actions, versioned in source control, but no bespoke UI. VS Code workflow.
Custom engine agent Pro-code (heavy) Your own surface You need to bring your own model / orchestration and control the full LLM loop. Most effort.
Rule of thumb: Choose SPFx when the value is in rich, interactive UI rendered inside Copilot (or a full-screen app) plus real SharePoint/Graph actions, and your team is a pro-dev SPFx shop. Don't reach for SPFx when the job is pure Q&A over documents (Agent Builder), a citizen-dev conversational flow (Copilot Studio), an API-action agent with no UI (Agents Toolkit), or you need your own LLM (custom engine). If there's no custom UI requirement, a lighter option ships faster.

05 Project anatomy - what got built & why

A Copilot App is made of three zones. Expand each one to see the files it contains and what each file is for. The full write-up is in docs/03, and every JSON property of the agent files is listed in docs/06.

Zone 1 - src/copilotComponents/helloAgent/ (your code)
FileWhat it is
HelloAgentCopilotComponent.ts(x) The component class. It is the entry point Copilot loads. It extends BaseCopilotComponent. Its only jobs are to read the host context (such as the current display mode and theme), mount your React UI, and switch between the inline and fullscreen layouts. Keep this file small and put the real UI in components/.
...CopilotComponent.manifest.json The component manifest. It is the contract Copilot reads. It declares the component id, its type (CopilotComponent, Ux), the display modes it supports, and the list of tools. This is what makes your component discoverable and callable from an agent.
...ComponentProperties.ts The tool's parameter schema, written with Zod. It checks the arguments the model sends to a tool, and it tells the model exactly what shape those arguments should take.
components/ Your actual React UI. This is where you spend most of your time. Both the small inline card and the full-screen app live here.
loc/ Localized strings. The standard SPFx pattern for translatable text, using a strings file plus a matching type definition.
Zone 2 - copilot/ (the declarative agent)
FileWhat it is
manifest.json The Microsoft 365 app manifest. It gives the package its identity in the tenant (name, icons, and IDs) and points Copilot at the declarative agent definition.
declarativeAgent.json The declarative agent definition. Think of it as the agent's brain. It holds the agent's name, description, instructions, conversation starters, knowledge sources, and the actions it is allowed to call.
ai-plugin.json The plugin definition. It describes your component's tools to the model as callable actions. It is the bridge between the agent and your tool.
instruction.txt The agent's behaviour, written in plain language. It sets the persona and the guardrails. Editing this file is the fastest way to change how the agent responds, with no code change needed.
Zone 3 - config/ and the root (build and packaging)
FileWhat it is
config/copilot-agent.json Links your components into the agent. It groups one or more components by their id. At build time it is merged with declarativeAgent.json to produce the final agent.
config/package-solution.json The packaging settings. It holds the solution id and version. Bump the version on every deploy. It also enables in-tenant hosting of your bundled files.
package.json Dependencies and build scripts. The scripts use Heft. Gulp is no longer used from SPFx 1.22 onward.
.yo-rc.json A record of your generator answers. It stores the SPFx version and component type you chose. Do not edit it by hand.
lib/ dist/ temp/ sharepoint/ Generated build output. temp/copilot/ holds the merged agent, and sharepoint/solution/*.sppkg is the package you deploy.
How a request actually flows 
User types in Copilot
   → declarative agent (declarativeAgent.json + instruction.txt) decides to act
   → invokes an ACTION (ai-plugin.json)
   → mapped to a TOOL on your component (component manifest tools[])
   → your component render()s UI in the Copilot canvas
   → inline by default; requestDisplayModeAsync('fullscreen') to "open the full app"

06 Build, run & deploy cheat-sheet

Heft toolchain (no gulp). Full detail: docs/04.

① Test locally

Run npm install once first. In the Copilot Workbench - seconds per iteration.

npx heft start --nobrowser

Open /_layouts/15/copilotworkbench.aspx → accept debug manifests → activate → Fire turn.

② Package

Bump solution.version first, then:

npx heft clean
npx heft build --production
npx heft package-solution --production

Output: sharepoint/solution/*.sppkg

③ Deploy → Copilot

App Catalog → upload .sppkg → approve any Graph perms → Add to Teams (auto-syncs the agent) → appears in M365 Copilot.

Always bump the version. SharePoint distinguishes packages by solution.version in package-solution.json. Skip the bump and the tenant may serve stale code.

08 Best practices & gotchas

The short version. Full list: docs/05.

Pin your versions

Use Node 22, React 18 (installed with --save-exact), TypeScript 5.x, and Fluent UI v8. Do not use Fluent UI v9. Version drift is the most common cause of the React #300 error.

Use Heft, not gulp

The build tool changed in SPFx 1.22. Run npx heft start, npx heft build, and npx heft package-solution instead of the old gulp commands. Heft is a local dependency, so prefix with npx (or use npm start).

Design both display modes

Make the inline view compact with a single clear action, and make the fullscreen view the full app. You request fullscreen, and you handle the host collapsing you back in onHostContextChanged().

Keep the component class thin

The class should only read host context, mount React, and wire up the display modes. Keep all of your real UI in the components/ folder.

Put behavior in text

Change instruction.txt before you change code. Keep each tool narrow, and keep ai-plugin.json in sync with your component's tools.

Practise preview hygiene

Build on a sandbox tenant only. Note which generator beta you scaffolded on, and trust your own scaffold over any document when they disagree.

Centralize data access

Use one PnPjs service and import only the parts you need. Cache your Graph reads, and show friendly error messages rather than raw stack traces in the Copilot UI.

CSP-ready

Do not use inline scripts or eval. Bundled assets in ClientSideAssets are trusted automatically, so keep all logic in bundled files.

Using an AI coding assistant as you build? Give it the pinned stack in Best practices first, so you don't get regressed to gulp / Node 18 / React 17. Mention which generator beta you're on if behavior diverges from these docs.
SPFx Copilot Apps are in preview. Always verify against your own scaffold and the official Microsoft Learn docs, because the APIs can change.
